# QA Report — role-based flow testing

**Date:** 2026-10-03
**Method:** five agents, one per role (Partner, Manager, Junior CA, Article, Admin), each driving the API as that user through a full working day on a seeded firm: 3 clients, 2 engagements, tasks, compliance assignments, 5 users. Plus a sixth pass covering new-firm setup and cross-tenant isolation.
**Verification:** every CRITICAL and HIGH below was independently re-confirmed against the code or the database before being listed. Four agent claims were wrong or environment-specific and have been corrected — see *Corrections* at the end.

---

## 1. The headline: role permissions are not enforced

**Severity: CRITICAL. One root cause, ~15 reported symptoms.**

`PermissionService` implements the full role × resource × action matrix, including `all` / `assigned` / `own` scope. It is correct and unit-tested. It is also **never called**: `grep -rn "PermissionService" apps/api/src` returns hits only inside `src/permission/` itself.

The matrix in `packages/shared/src/constants/role-permissions.ts` and the seeded `firm_role_permissions` table are, today, dead configuration.

What that means in practice — all independently reproduced:

| Reported by | Action | Expected | Actual |
|---|---|---|---|
| Manager, Article | `DELETE /api/clients/:id` as ARTICLE | 403 | **204, client deleted** |
| Article | `POST /api/clients` as ARTICLE | 403 | **201** |
| Junior, Article | `GET /api/clients` as ARTICLE/JUNIOR | only assigned | **all 9 firm clients** |
| Junior, Article | `GET /api/tasks` as ARTICLE/JUNIOR | only assigned | **all 16 firm tasks** |
| Junior | `PATCH /api/clients/:id` on an unassigned client | 403 | **200, write applied** |
| Article | `PATCH /api/tasks/:id` on another user's task | 403 | **200, title changed** |
| Article | `PATCH /api/tasks/:id {assigneeId}` (no `task:assign`) | 403 | **200, reassigned** |

Supporting evidence in code:
- `client.controller.ts: deleteClient` has no `@Roles()` and no permission check.
- `client.service.ts: listClients` and `task.service.ts: listTasks` build their Prisma `where` from query params only — there is no clause tying results to the caller.
- **32 of 46 mutation endpoints have no role guard** (10 have `@Roles`, 4 are `@Public`). Some of those 32 are legitimately open (logout, change-password, mark-notification-read, own-leave, comments). The dangerous set is client / engagement / task create-update-delete, compliance assignments, checklist and dependency mutations.

**What is NOT broken:** tenant isolation. `firm_id` scoping is applied automatically by the Prisma `$extends` extension in `prisma.extensions.ts`, and cross-firm reads and writes correctly returned 404 across clients, tasks and engagements. Nothing leaks between firms. The entire exposure is *within* a single firm.

This is one architectural gap — a guard or query helper that consults `PermissionService` — not 32 separate fixes.

## 2. Identity and tenancy

**Cross-firm duplicate email can be created** — CRITICAL
`POST /api/users` checks email uniqueness with the *firm-scoped* Prisma client (`user.service.ts:102`), so it only rejects duplicates inside the firm. `auth.service.ts:55` checks the same thing with `prisma.unscoped` — globally. Two users with the same email in different firms now exist in the local DB (verified by SQL).
Login resolves users with `findFirst` on email alone (`auth.service.ts:176`), with no firm disambiguation and no ordering — so it always returns one of the two and the other account becomes unreachable. Which one is not deterministic.
*(The reporting agent claimed the supplied password selects the firm. That is not what the code does, and I could not reproduce it — both logins returned 401, consistent with the lockout counter tripped by its own earlier attempts. The duplicate-creation bug is real; the "password routes you" characterisation is not.)*

**500 + raw ORM error on cross-tenant user PATCH** — HIGH
`PATCH /api/users/:id` and `/deactivate` with another firm's user id return `500 {"message":"No User found","error":"NotFoundError"}`. `user.service.ts:141,189` use `findUniqueOrThrow` without translating Prisma's `NotFoundError` into `NotFoundException`. No data leaks, but it is an unhandled 500 on the tenant boundary, and clients/tasks/engagements return a clean 404 on the same probe.

## 3. Correctness and data integrity

**Invalid enum in a task filter returns 500** — HIGH
`GET /api/tasks?status=NOT_A_STATUS` → 500 `PrismaClientValidationError`. Same for `priority`, and for partially valid lists like `status=TO_DO,BOGUS`. `ListTasksQueryDto` types these as `@IsString()` and splits them straight into a Prisma `in:` with no enum check. Reachable by hand-editing a URL — and `TaskList` writes filters into the URL, so a stale or shared link can 500.

**No PAN uniqueness within a firm** — HIGH *(verified directly)*
Two clients in one firm were created with identical PAN `AAADP1111Z`, both 201. PAN is a statutory identifier; duplicate client *names* are already rejected with 409, so the inconsistency looks unintended rather than deliberate.

**Engagement accepts an inverted period** — HIGH *(verified directly)*
`periodStart` 2026-10-31 with `periodEnd` 2026-10-01 saved with 201. No cross-field validation, and compliance period maths runs off these dates.

**Leave write-path returns "Unknown User"** — MEDIUM *(reported independently by all five agents)*
`POST /api/team/leave` responds with `"userName":"Unknown User"`; approve/reject respond with `"approvedByName":null`. The list endpoint resolves both correctly. `leave.service.ts` calls `toDto(record, new Map())` on create/approve/reject/cancel while `list()` builds a real user map.

**Whitespace-only values pass validation** — MEDIUM
`{"label":"   "}` and `{"body":"    "}` are accepted (201) and persist as blank-looking rows. A true empty string is correctly rejected. `@IsNotEmpty` does not trim.

**No way to reactivate a deactivated user** — HIGH
`PATCH /users/:id/deactivate` exists; nothing reverses it. `isActive` is rejected by `UpdateUserDto`. A user deactivated by mistake is permanently locked out via the API. The deactivation guards themselves are good (last-partner blocked, double-deactivate blocked).

**ADMIN can delete but cannot restore** — MEDIUM
`/recently-deleted` list is `@Roles(PARTNER, ADMIN)` but restore is `@Roles(PARTNER)`. Admin can delete a client and see it in the bin, but cannot undo its own delete.

**Audit log entityType filter is case-sensitive** — LOW
`?entityType=Task` silently returns an empty set; stored values are lowercase. Reads as "no audit trail" rather than "no match".

## 4. Suggestions worth considering

- Add one RBAC regression test per resource: log in as JUNIOR_CA, hit list/get/edit/delete on a record that is not theirs, assert 403 or filtered. A single such test per resource would have caught section 1 immediately.
- Decide explicitly whether `UNDER_REVIEW → DONE` should be available to the assignee. The transition is legal by design; what is missing is the role check on *who* performs it.
- Make `restore` return 200 rather than 201 — it updates an existing resource.
- Consider a floor on `dueDate`; tasks dated 2020 are accepted silently.
- Align idempotency: revoking a dead invite twice is a silent 204/204, deactivating twice is a 400.
- `RoleGuide` (the invite-screen panel added earlier today) advertises credential access per role, but `CredentialModule` is not registered in `app.module.ts` — the credential locker has a DB model and no API. Either drop that line or mark it as upcoming. **This one is mine to fix.**

## 5. What worked well

Worth recording, because it is most of the product:

- Tenant isolation across clients, tasks and engagements — consistently 404, no payload leakage, firm-filter query params hard-rejected.
- Task status machine: invalid transitions cleanly rejected, DONE correctly blocked with 409 while a required checklist item is incomplete.
- Business-rule guards: deleting a client with an active engagement (409, clear message), deactivating the last partner (409), revoking an accepted invite (400), duplicate client name (409).
- Compliance: calendar, suggestions, assignments, compute-on-read entries and status updates all behaved correctly and consistently.
- Audit log attributes the right actor, entity and timestamp across create/delete/settings/invite actions.
- Full partner lifecycle: client → engagement → tasks → reassignment → status walk → delete → recently-deleted → restore.
- Input handling: 5000-char comment boundary exact, over-limit cleanly 400, SQL-injection-style search strings safe, emoji and Devanagari stored and returned correctly.
- `@Roles`-guarded routes (invites, firm settings, user deactivation, leave approval) returned clean 403s with no leakage — the guard works where it is applied, which is why section 1 is a wiring gap and not a broken mechanism.
- Dashboard counts and team workload matched the underlying task data.
- New-firm registration and first-run path completed first try with no undocumented required fields.

## 6. Corrections to agent reports

Recorded so the report is not trusted further than the evidence supports:

1. **"ARTICLE can skip PARTNER_APPROVAL" is not a workflow bug.** `UNDER_REVIEW → DONE` is explicitly legal in `TASK_STATUS_TRANSITIONS`. The real issue is the missing role check on who may do it — already covered in section 1.
2. **"New firms get no engagement-type catalog" is a local artifact.** The local DB had been truncated by the e2e suite. Production (Neon) has 11 global engagement types, 21 statutory deadlines and 1 task template, all correctly `firm_id IS NULL`.
3. **"Password selects which firm you log into" is not supported by the code.** See section 2.
4. **"500 leaks a local file path" is expected in dev now.** A change earlier today deliberately exposes internals outside production and returns generic text in production. The 500 itself is still a bug.

## 7. Environment note

The e2e suite runs serially against the **dev** database and `TRUNCATE`s between tests — it wiped the seeded firm mid-session. Harmless today (it is all test data), worth separating before the first real client.
